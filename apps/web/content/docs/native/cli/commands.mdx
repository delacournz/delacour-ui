```bash
delacour <command> [components...] [options]
```

Every command that reads the registry also takes `--registry`, `--ref`, `--offline` and `--cwd`.
The blocks below are that command's own `--help`.

## init

Sets the project up and writes `native-components.json`. Covered in full at
[Setting up a project](/docs/native/cli/init).

<InstallTabs commands={[{ verb: "dlx", packages: ["delacour@latest init"] }]} />

**Options**

```txt
Usage: delacour init [options] [components...]

set this project up and write native-components.json

Arguments:
  components             components to add straight away

Options:
  -y, --yes              accept every default without asking
  -d, --defaults         use the default layout without asking
  -f, --force            rewrite an existing native-components.json
  -s, --src <dir>        base directory for source files
  --package-name <name>  put the components in a shared package with this name
  --package-path <dir>   where that package goes, relative to the workspace root
                         (default: "packages/ui")
  --install              install the packages the components need, without asking
  --no-install           write the files and install nothing
  --silent               print nothing but errors
  --registry <url>       registry to read from: a URL, github:owner/repo, or a
                         local path
  --ref <ref>            git ref to read the registry at (default: "main")
  --offline              use only what is already cached
  -c, --cwd <path>       directory to work in (default: the current directory)
  -h, --help             display help for command
```

## add

Copies components in, with everything they need.

<InstallTabs commands={[{ verb: "dlx", packages: ["delacour@latest add button input field"] }]} />

```bash
delacour add --all
```

The order is deliberate: resolve the dependency graph, plan every file, ask **once** about
conflicts, write, then report what the components need from npm. Installing first would leave a
project holding new native dependencies and no components if you answered "no" to the overwrite
prompt.

A file already on disk with byte-identical content is not a conflict — that is the normal state of
a utility two components share. Non-interactively, a genuine difference is an error naming the
files rather than a silent overwrite; pass `--overwrite` when you mean it.

### What it needs installed

Every `add` ends with the packages the components need, whether or not anything is missing:

```txt
●  Needs 14 external packages, 2 not here yet:
│    bunx expo install @gorhom/bottom-sheet react-native-keyboard-controller
│    already installed — clsx, react-native-reanimated, react-native-svg, tailwind-variants, …
```

The missing ones are shown as commands rather than as a list of names, because the command is the
part that is not obvious — and they are spelled for the package manager this project is actually
on.

Then it asks. `--install` answers yes without asking, `--no-install` answers no, and a run with
nobody to ask — a script, CI, an agent — installs nothing and prints the commands instead. Copying
source into your repository is local and reversible; running your package manager is neither.

<Callout title="Dependencies are split three ways">
`expo install` for native modules and anything pinned to the SDK, your package manager for plain
JavaScript, and `registryDependencies` — which are other components to copy, not packages to
install.
</Callout>

<Callout type="warn" title="Install into the app, not the shared package">
If your components live in a package several apps share, the packages still belong to the **app**.
A native module resolved from two places registers twice and breaks at runtime — which is why `add`
runs the install from the app root, and records the same packages as `peerDependencies` on the
shared package rather than as dependencies.
</Callout>

**Options**

```txt
Options:
```

## view

Prints an item's files, the components it copies in, and the packages it installs.

```bash
delacour view button
```

```txt
Button  button
A pressable action composed from parts, with variants, sizes and a loading state.

files      ui/button/button.tsx
           ui/button/index.ts
           …
copies in  styles, cn, tv, color, use-theme-color, icon, compose-refs, merge-props, pressable, spinner, text

needs installing
  bunx expo install react-native-gesture-handler react-native-pulsar react-native-reanimated react-native-svg react-native-worklets uniwind
  bun add clsx tailwind-merge tailwind-variants tailwindcss
```

The install lines cover the **whole closure**, not the item's own dependencies. `button` declares
only `tailwind-variants`; it renders `icon`, which needs `react-native-svg`, and `pressable`, which
needs Gesture Handler. Listing an item's own packages would under-report what `add` installs by
exactly the ones you are deciding about.

**Options**

```txt

show one item and what it pulls in

Options:
  --json            print JSON
  --registry <url>  registry to read from: a URL, github:owner/repo, or a local
                    path
  --ref <ref>       git ref to read the registry at (default: "main")
  --offline         use only what is already cached
  -c, --cwd <path>  directory to work in (default: the current directory)
```

## diff

Shows what has moved upstream since you copied a component.

```bash
delacour diff
delacour diff button
```

Read-only, and deliberately so. Once a component is in your repository it is yours, and the changes
on each side are both legitimate — a fix upstream, a tweak locally. Printing both and stopping is
the only behaviour that does not quietly pick a winner. `add <name> --overwrite` takes the
registry's copy when that is what you want.

**Options**

```txt
Usage: delacour diff [options] [name]

show what has changed upstream since these files were copied

Arguments:
  name              one component, or every installed one

Options:
  --silent          print nothing but errors
  --registry <url>  registry to read from: a URL, github:owner/repo, or a local
                    path
  --ref <ref>       git ref to read the registry at (default: "main")
  --offline         use only what is already cached
  -c, --cwd <path>  directory to work in (default: the current directory)
  -h, --help        display help for command
```

## doctor

Checks that the app is wired up for these components. Every check is a failure mode that produces no
error on its own — see [Troubleshooting](/docs/native/cli/troubleshooting). Exits non-zero when a
check fails, so it works in CI.

```bash
delacour doctor
```

**Options**

```txt
Usage: delacour doctor [options]

check that this Expo app is wired up for these components

Options:
  -c, --cwd <path>  directory to work in (default: the current directory)
  --json            print JSON
  --fast            skip the checks that shell out to the Expo CLI
  --silent          print nothing but errors
  -h, --help        display help for command
```

## Shared options

`--cwd` decides which `native-components.json` applies: the nearest one, walking upwards. The walk
stops at the repository root — past it lie your other projects.

See [The registry](/docs/native/cli/registry) for pinning a ref and pointing at a fork.
